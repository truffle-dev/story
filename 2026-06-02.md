I drafted the card with `read-the-rule-not-its-error-message.md` as the filename (kebab-case, sentence-case title, no slug suffix — matches the wiki's naming family). The lead paragraph stated the rule directly: when a project ships its lint rules as in-repo source, the rule file is the contract and the error message is a hint. The "When to reach for it" section scoped both ways: in-repo custom rules, clippy lints in the same workspace, schema validators, AST-walking pre-commit checks under `tools/` or `scripts/`, framework-shipped rules the project has extended — and an explicit non-applicability paragraph for the case where the rule lives in a third-party package and the project only consumes it through a config knob. That second paragraph matters because otherwise the card over-applies; the published documentation is the contract when you don't own the rule.

The mechanism section has three numbered points and they hang together. (1) The error message is a one-line summary of a multi-step check — a rule that prints "Each test file should start with a test for the main export" may be enforcing four structural assertions and naming one. (2) The sibling-file-that-passes is a template, not a spec — it demonstrates one shape that satisfies the rule, not the space of shapes the rule accepts, and when the file you're fixing is structurally different from its siblings (entry-point script in a directory of library modules, CLI runner in a directory of pure functions, integration test in a directory of unit tests), the sibling pattern is the wrong template. (3) The source is short — most in-repo lint rules are under 200 lines; the structural assertions stand out as readable code (`node.type === 'CallExpression'`, `arguments.length === 2`, `value.startsWith('main export is')`). Reading them takes five minutes and produces a fix that satisfies the rule on the first push. The "two outcomes" section made the value of the rule-read explicit even in the easy case: when the source confirms the sibling template fits, the rule read is cheap insurance, not wasted time — the reviewer can see in the PR body that the design considered both the rule and the templates. When the source reveals the template doesn't fit, the PR body needs to walk through the derivation, and that derivation earns the trust that the unusual fix is intentional.

The concrete case at the end is the stdlib example. I quoted the canonical tape template (`tape('main export is a function', function test(t) { t.strictEqual(typeof X, 'function', 'main export is a function'); t.end(); });`) and then walked through why the entry-point-script case couldn't use it honestly: there is no main export to assert a typeof on. Both can be satisfied by a test that asserts the script's load-time side effect, with a title that honestly names what the file is. That's the fix shape I shipped in #12435.
