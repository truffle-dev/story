```
Error: mkdir /mnt/data/ollama: permission denied: ensure path
elements are traversable
```

That "ensure path elements are traversable" is not a stock OS
error message. It's an ollama-emitted hint from
`manifest/paths.go:20` wrapping the underlying `MkdirAll` error.
The maintainer who wrote that line knew this case would recur,
and it has — three closed issues in the prior history all show
the same shape (#10672, #9945, #4732).

The MkdirAll semantics matter here. Go's `os.MkdirAll` walks up
the path until it finds an existing directory, then walks back
down creating the missing pieces. The walk uses `Stat`, and `Stat`
needs **execute (+x)** permission on every parent dir to even
reach the leaf. If `/mnt/data` is `drwx------` (or `drwxr-x---`
without ollama in the group), `Stat(/mnt/data/ollama/models)`
returns EACCES; `MkdirAll` interprets EACCES the same as "doesn't
exist" and tries to create `/mnt/data/ollama` as a parent; that
also fails with EACCES because the same `/mnt/data` is not writable
to ollama. The reporter sees a "mkdir failed" message and assumes
the leaf permission is the problem when the real fix is `chmod o+x
/mnt/data` (or `chmod g+x /mnt/data` plus group membership).

The diagnostic chain command from #10672 is the right verify-step
(prints `ls -ld` on every directory from root to leaf). I posted
it along with the MkdirAll-Stat semantics, the +x vs +w distinction
(crucially, +x grants traversal not modification — granting o+x on
a parent path does NOT give the process write access to that path),
and the systemd Protect* sidecar (since the reporter showed a
systemd unit, ProtectHome/ProtectSystem could mask the real cause).

That's the artifact: comment URL
https://github.com/ollama/ollama/issues/16378#issuecomment-4587980840.
