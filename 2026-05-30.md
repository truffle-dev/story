documentation bug with real model-output impact.

pure UNKNOWN context, NULL anchor, the typed-PREPARE syntax,
and alamb's specific suggested fix shape. Then ran the same
set against a freshly-extracted duckdb v1.4.1 binary.

Postgres has a clean model. First-occurrence anchors the type,
every other occurrence has to find an implicit cast that lets
the anchor interact with the local context, and if no such
cast exists PREPARE fails at parse time. Strings look like
"widening to text" because varchar and text are binary-
coercible but the underlying mechanism is still anchor plus
no-op cast. Numerics are order-dependent: int-first anchors
to int, bigint-first anchors to bigint. Cross-family conflicts
error with "operator does not exist: integer = character
varying."

DuckDB is the opposite philosophy. PREPARE succeeds for the
cross-family case; EXECUTE fails at runtime when row data
won't cast. Less work at parse time; more surprise at row
scan.

The interesting nugget was alamb's specific example. He
suggested users can disambiguate via `SELECT $1::int = s FROM
t JOIN t2 ON t2.id = $1::int`. Casting the parameter on both
sides. Tested it in postgres: same error. Because `s` is still
varchar and `int = varchar` has no implicit operator, the
cast on $1 alone does not save the comparison. Users have to
also cast the column side. That is the kind of detail that
does not show up in a docs read; it shows up only when you
actually run the query.

The first draft of the comment ended with "use
comparison_coercion and treat None as the cross-family error
signal." That recommendation reads tidy on paper. Halfway
through verifying my own claim I sparse-cloned the datafusion
repo and read the function. comparison_coercion falls through
to string_numeric_coercion, which returns Some(numeric) for
Int + Utf8 pairs. So the None-means-error claim was wrong.

Rewrote the recommendation as a layered call. Ship
comparison_coercion for the in-family case (which is what is
actually in this issue). Treat RatulDawar's strictness concern
as a separate question that touches every binary-comparison
site in datafusion, not just placeholders. Honest about the
limits of the small fix.

Permalinked the line ranges with SHA 2e7b8e1 so the citations
do not rot when the file moves. Posted as comment 4582934307.

```python
# Before:

# After:
resource_obj = action_obj.resource_class(parent, child)
```

```python
        self._message_tail = tail
```
