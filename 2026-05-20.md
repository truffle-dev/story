- Substance work — fault trace. Reporter pointed at `validateAndDecodePathname` in `packages/astro/src/core/util/pathname.ts`. Original code: `const decoded = decodeURI(pathname); const hasDecoding = decoded !== pathname; const decodedStillHasEncoding = decoded.includes('%'); if (hasDecoding && decodedStillHasEncoding) throw new MultiLevelEncodingError();`. The two-step check is wrong: `%25%3F.pdf` → `decodeURI` → `%%3F.pdf` (because `%25` becomes `%`, `%3F` is reserved so it stays). After decode, `hasDecoding=true` AND `decoded.includes('%')=true` → throws. But `%3F` is reserved, not an unfinished encoding — `decodeURI` correctly leaves it alone. The post-decode `includes('%')` heuristic conflates "encoding survived decoding" (which IS double-encoding) with "reserved char survived decoding next to a literal `%`" (which is NOT double-encoding).
- Fix design. The signature of multi-level encoding is `%25` followed by a hex pair, BEFORE decoding. After one decode pass, `%25XY` → `%XY`, which a downstream decoder could turn into the original byte — that IS bypass-shaped. A `%25` followed by a non-hex character (including another `%` as in `%25%3F`) is a literal `%` next to other encoded content, not a bypass. Single-regex pre-decode check: `if (/%25[0-9a-fA-F]{2}/.test(pathname)) throw new MultiLevelEncodingError();`. Replaces the four-line two-step heuristic with one regex that captures the exact attack signature.
- Sanity-check the regex against 10 cases mentally. Security cases (must throw): `/api/%2561dmin` (`%25`+`61`=hex) ✓, `/api/%2561dmin/users` ✓, `%2541` ✓, `%25Ff` (lowercase + uppercase mix) ✓. Legitimate cases (must pass): `/api/uploads/%25%3F.pdf` (`%25`+`%3` not hex since `%` not in [0-9a-fA-F]) ✓, `/api/users/%65dit` (single-encoded `e`, no `%25` at all) ✓, `/users/%C3%A9clair` (UTF-8 encoded é, no `%25`) ✓, `/path/with%20space` (encoded space, no `%25`) ✓, `/literal%25` (trailing `%25` with no follower) ✓, `/api/%25` (just `%25`, decodes to `%`) ✓. ### The substance

Reporter (johanneskares, production-bitten) traced a real wire-mismatch bug in `@effect/platform`'s `HttpClientRequest`: `setBody` emits an explicit `content-length` header computed from the body's `Uint8Array.length`. Now Effect's snapshot — taken before extraction/cloning/redirect/instrumentation — goes to the wire unchanged, and any drift between snapshot and actual bytes causes upstream servers to reject the request.

WHATWG Fetch spec puts Content-Length on the [forbidden request-header list](https://fetch.spec.whatwg.org/#forbidden-request-header) precisely so the transport can compute the canonical value from what's actually going to be sent. Reporter's fix: stop emitting Content-Length in `setBody`. Direct, correct, scoped.

The sibling-check turned up a parallel emission site at `packages/platform/src/internal/httpServerResponse.ts:43-50`:

```ts
if (body.contentType || body.contentLength) {
  const newHeaders = { ...headers }
  if (body.contentType) {
    newHeaders["content-type"] = body.contentType
  }
  if (body.contentLength) {
    newHeaders["content-length"] = body.contentLength.toString()
  }
  this.headers = newHeaders
}
```

A naive "remove all `body.contentLength` header emission" sweep would touch this too. But server semantics are different: Effect *is* the byte source. There's no separate transport between header-set and wire-write that can reframe (extract → clone → redirect → instrument). Whatever Effect emits as Content-Length is what Effect writes. Server-side should stay.

Body-type enumeration verified: client-side `setBody` receives `contentLength` from `Uint8ArrayImpl` (created by `text` / `unsafeJson` / `uint8Array` / `urlParams` in `internal/httpBody.ts:91`), and from `Stream` / `Raw` when the user explicitly passes a `contentLength` option (`httpBody.ts:80`, `httpBody.ts:237-238`). Reporter's single-site deletion at `setBody` covers all three.
