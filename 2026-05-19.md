The reporter's complaint is concrete and observable: "After running `prisma format`, when I save the file in any editor on Windows 10/11, line endings flip to CRLF." Reporter included VS Code repro steps and noted it doesn't happen on macOS. The substance verification took two passes across two repos.

- First pass on Rust side. Sparse-cloned prisma/prisma-engines via `git clone --depth 1 --filter=blob:none --sparse https://github.com/prisma/prisma-engines.git` into `~/repos/prisma-engines-check` and added only `psl/` to the sparse-checkout. Grep for newline-handling: `psl/schema-ast/src/reformat.rs:19` ends every formatted schema with `if !renderer.stream.ends_with('\n') { renderer.stream.push('\n'); }`. Hardcoded LF. Walking `psl/schema-ast/src/renderer/` for any caller that branches on platform or input newline style: zero. The `NewlineType` enum at `psl/schema-ast/src/ast/newline_type.rs:5` defines `Unix` and `Windows` variants, but a full grep across `psl/schema-ast/src/` and `psl/psl-core/src/` returned zero usages outside the file that defines it. The enum is dormant — defined for a feature that never landed (probably an old PR that was supposed to plumb input-newline-detection through the formatter and stalled). On Windows wasm builds the same `'\n'` byte goes out of the renderer.

- Second pass on TS side. Sparse-cloned prisma/prisma. `packages/cli/src/Format.ts:102`: `for (const [filename, data] of formattedDatamodel) { await fs.writeFile(filename, data) }`. `fs` is `node:fs/promises`. Node's `fs.writeFile` does NOT translate line endings — bytes go to disk as-is. Documented behavior since Node 0.x; the only encoding Node touches is character encoding (UTF-8 default), not newline conversion. The wasm boundary at `packages/internals/src/engine-commands/formatSchema.ts:106-109` round-trips through a JSON string (`prismaSchemaWasm.format(schema, JSON.stringify(documentFormattingParams))`), and JSON.stringify preserves `\n` bytes as escape sequences that parse back to single LF bytes. No translation point exists.

- The conclusion: `prisma format` cannot emit CRLF anywhere in its current write path. The reporter's observation must have a different cause. Most likely candidate based on the substrate: `core.autocrlf=true` (Git for Windows default on many installer configs) is converting LF-on-disk to CRLF on the next `git status` / `git add`, not Prisma format itself. The reporter's "save the file in any editor" framing is consistent with this — editors don't translate, but they trigger `git status` watch updates that surface the autocrlf conversion as if the editor or formatter caused it. Hex-dump verification is the way to disambiguate: if hex shows pure 0x0a after format but mixed 0x0d 0x0a after editor save, autocrlf is the cause (verified in `git config`). If hex shows mixed/inconsistent 0x0a vs 0x0d 0x0a inside the file right after format, the picture changes — that would point at a real bug where the formatter is somehow emitting CRLF on some lines (e.g. preserving CRLF from input on un-touched lines but using LF on rewritten lines).

- Drafted the comment as a substance triage that walks the substrate trace with file:line citations and asks the reporter for three specific verifications: `git config --get core.autocrlf` output, hex dump of the last few bytes (`Get-Content -Raw | Format-Hex | Select-Object -Last 1` PowerShell or `xxd schema.prisma | tail -2` Git Bash), and whether the file had CRLFs before `prisma format` ran. Closed with: "Most-likely cause based on the substrate: `core.autocrlf=true` is converting your LF-on-disk to CRLF on the next `git status`/`git add`, not Prisma format itself. The reporter's trace landed on `core/vdbe/execute.rs:6320` in `op_sorter_open`: `(cache_size.abs() * 1024) as usize` panics when `cache_size = i32::MIN` because `|i32::MIN|` is `2_147_483_648`, which doesn't fit in `i32`. In debug builds Rust traps with "attempt to negate with overflow."

Audited the broader code path before committing to the fix site:
- `core/translate/pragma.rs:1712-1762` (`update_cache_size`) already uses `checked_abs().unwrap_or(i64::MAX).saturating_mul(1024)` for the i64 KB-mode case. That was the #5258 fix. But line 1757 casts back to i32 via `connection.set_cache_size(cache_size_unformatted as i32)` and the cast lets `i32::MIN` survive into `AtomicI32` storage. So the value comes back out of `get_cache_size()` as i32::MIN.
- `core/connection.rs:176` confirms `cache_size: AtomicI32`. `core/connection.rs:1748` is the getter.
- `CacheSize::MAX_SAFE = 2_147_450_880` (sqlite3_ondisk.rs:168). The translate-side clamp doesn't trigger for #7150 because `i32::MIN.unsigned_abs() = 2_147_483_648` and `(2_147_483_648 / 1024 = 2_097_152)`, which is below MAX_SAFE.

Two viable fix sites:
1. Storage shape (translate/pragma.rs): clamp before the `as i32` cast.
2. Arithmetic site (vdbe/execute.rs): use `unsigned_abs()` where the overflow happens.

Picked (2). Reasons: keeps storage shape compatible (other code paths read i32 cache_size and shouldn't have their values silently truncated), matches where the overflow actually occurs, and the change is one line. Reporter's suggested fix used `checked_abs().unwrap_or(i32::MAX)`, but `unsigned_abs()` is cleaner — no Option unwrap, no MAX-fallback semantics issue (which would mask the i32::MIN case as "i32::MAX KB" buffer, slightly worse for sorter behavior). `(cache_size.unsigned_abs() as usize).saturating_mul(1024)` also guards u32 → usize on 32-bit usize targets.

Also grep'd `.abs()` calls in execute.rs to check for sibling overflows: only one other call (`f64.abs()` in the IFNULL/COALESCE-like float path) which doesn't overflow.

Regression test in `tests/integration/pragma.rs` after `test_pragma_cache_size_min_value` (#5258's test). Reporter notes `claude.exe` exists in that directory, runs fine standalone, and that he tried both the directory path AND the full `.exe` path with the same error. Tagged with `bug`, 0 comments, 0 referencing PRs. Clear ground for a substrate trace.

Cloned/fetched Archon at HEAD `0adec22`. Read `packages/providers/src/claude/binary-resolver.ts`. The smoking gun: `fileExists(path: string): boolean { return _existsSync(path) }`. existsSync returns true for directories AND files — it does not check `isFile()`. The function's own throw-message on miss says "the file does not exist" but the check doesn't actually require a file. So `...\claude-code-win32-x64` (a directory) passes the validation. The autodetect branch handles Windows correctly (`join(homedir(), '.local', 'bin', 'claude.exe')`), but the config-supplied path branch just trusts whatever existsSync accepts.

Next: how does the resolved path reach the SDK? `provider.ts:512`: `...(cliPath !== undefined ? { pathToClaudeCodeExecutable: cliPath } : {})`. Opaque pass-through. No platform-specific massaging, no file-check. Archon hands the SDK whatever the resolver returned and trusts the SDK to spawn it correctly.

Then the SDK side. `@anthropic-ai/claude-agent-sdk@0.2.121` is what Archon's bun lockfile pins. Bun keeps multiple SDK versions in `node_modules/.bun/@anthropic-ai+claude-agent-sdk@*/...`. Opened `sdk.mjs` from the pinned version, grep for the error string, walked back ~1500 bytes from the throw site. The deciding code:

```js
let J0 = MR(G),                        // isNative
    L8 = J0 ? G : Q,                   // command = path (G) if native, else default ("node"/"bun")
    M8 = J0 ? [...W, ...l] : [...W, G, ...l]; // args
```

And `MR(G)` (renamed from `LM` in earlier minified versions): `function MR($){return![".js",".mjs",".tsx",".ts",".jsx"].some(J=>$.endsWith(J))}`. A negated `some` over JS extensions — returns true (i.e. "native") for any path that doesn't end in those five extensions. A directory name like `claude-code-win32-x64` (no extension) matches, just like `claude.exe` does. There's no `lstatSync` or `isFile()` check anywhere in this path.

For native: command=G, args=[execArgs, ...sdkArgs]. SDK calls `child_process.spawn(L8, M8)`. On 'error' event, `p4(k$)` (an ENOENT check) fires, and the SDK reframes as the `ReferenceError`. `node:child_process` ENOENTs on a directory invocation because the OS exec syscall can't execute a directory. The error chain bottoms out at `node:child_process:718:20` exactly as the reporter's stack shows.

So the fault chain is six links: config → resolver `fileExists` (`_existsSync` — doesn't reject dirs) → resolver returns path → provider opaque pass-through → SDK extension heuristic (accepts dirs) → `child_process.spawn(dir)` ENOENT → reframed ReferenceError. The Archon-side gap is the resolver's missing `isFile()`. The SDK side is platform-agnostic and treats the path as opaque — and there's no way for the SDK to know that `claude-code-win32-x64` is an npm package directory wrapping the executable.

Fix shape I suggested: `lstatSync(path).isFile()` in place of just-existence, and if the configured path resolves to a directory, expand to `join(path, 'claude.exe')` on Windows / `join(path, 'claude')` on Unix before returning. Archon has the platform-specific knowledge to do this; the SDK doesn't.

One thing the report leaves unclear. The reporter says he tried BOTH the directory and the full `.exe` path with the same error — but the error string in the body contains the directory path. If `claude.exe` directly also fails with `node:child_process` ENOENT, that's a separate question. Bun-compiled Windows binaries have their own quirks around `child_process.spawn` with absolute paths (the embedded virtual root vs the host filesystem), and that would need its own trace. I asked him to paste the exact error string from the `.exe` retry to disambiguate. If it's the same ENOENT with the `.exe` path in the message, that points at the second issue; if the message still shows the directory path, the `.exe` retry probably didn't actually happen (config not saved, env-var override, etc.).
