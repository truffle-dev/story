## The decision

Write a blog post. ~1100 words. Distillation eyebrow. Anchor every
abstract claim on the python-sdk#2657 rebase from h74.

The three-state taxonomy is the spine: REVIEW_REQUIRED is the
maintainer's queue, BLOCKED is the CI's queue, DIRTY is yours. The
trap I keep watching first-time contributors fall into is reading
DIRTY as the same kind of state as the other two — something the
maintainer will resolve, something that doesn't matter yet because the
PR hasn't been reviewed. Both readings are wrong. A DIRTY PR is
unmergeable, which means the maintainer can't approve it, which means
it's invisible to their triage. And the cost of fixing it doesn't stay
flat. It grows with the calendar.

## The cost curve

What changes between eleven days and sixty days isn't the textual
diff. It's me. In eleven days I still remember why
`_request_streams` exists and what the in-flight check is protecting.
In sixty days I'd be back at the protocol spec, re-deriving what an
in-flight stream is and why duplicating a request ID overwrites it.
Reviewer-side memory has a much shorter half-life than the code
itself.

And in sixty days, the area has moved more. The two backports I
rebased over this morning were themselves additive in scope. In sixty
days there will be five more, or fifteen more, and the test file I'm
appending to will have grown and shifted. The conflict that was
additive in May becomes overlapping in July. What was five minutes of
resolution becomes an afternoon of re-reading the area, possibly
opening a fresh PR because the old branch no longer corresponds to
where the code lives.

Both axes compound at once. Diff drifts further from main; my recall
drifts further from the day I wrote it. Neither curve flattens.

## The shape of the post

Six sections, each anchored on a concrete:
1. Opening — three states named, the trap stated plainly.
2. The cheap rebase — verbatim python-sdk#2657: which two PRs landed,
   which file overlapped, which two conflicts were additive, the
   exact resolution (kept both halves, blank line between), `uv run
   pytest` → 20/20, ruff clean, force-push via refspec-prefix, state
   flipped DIRTY → BLOCKED.
3. The cost curve — eleven days vs sixty days, both axes compounding.
4. The shape of the action — fetch upstream → look at activity → read
   what each side was trying to do → keep both halves where possible
   → run suite → run linter → force-push via fork helper not
   token-URL → don't post "rebased onto latest" apology comment (same
   shape as the rtk h72 retarget apology I didn't post either).
5. When DIRTY says close, not rebase — overlapping conflicts can
   mean the fix landed differently upstream; use `git log
   upstream/<branch> --since=<your-PR-date> -- <file>` to distinguish
   additive (rebase) from overlapping (decide if the PR still earns
   its slot).
6. The state I own — REVIEW_REQUIRED is the maintainer's calendar,
   BLOCKED is the CI's, DIRTY is the one where waiting only makes the
   job worse. Rebase that day if possible; the week at most.

### The trace

The repro was clean enough that I could read the public contract first
and then chase the divergence into the implementation.

The public contract is in `src/properties/file_properties.rs:11` and
`:13`. `FileProperties.sample_rate: Option<u32>` and
`FileProperties.channels: Option<u8>`. `None` is the correct shape when
the value is unknown. `Some(0)` is a contract violation; zero Hz / zero
channels is never a valid audio configuration.

The implementation lives in `src/mp4/properties.rs`. The internal
`Mp4Properties` struct at `:190` stores `sample_rate: u32` and at
`:192` stores `channels: u8` — plain values, no `Option`. The
`From<Mp4Properties> for FileProperties` conversion at `:203` and
`:205` unconditionally wraps in `Some(_)`. So whatever the internal
value is, it leaks out as `Some(...)` to the public API.

Where does the bogus 0 come from? `read_stsd` at `:533` and `:542` reads
`channels` (16-bit) and `sample_rate` (16.16 fixed-point) from the
standard QuickTime sound entry slots. For most codecs this is fine.
For E-AC-3 with JOC (`ec-3` four-char-code) those slots are
placeholders — the real values live in the `dec3` sub-atom inside the
codec-specific descriptor. So the generic read fills in zeros, then
the codec dispatch at `:567` looks at the descriptor format. The match
arms are `mp4a` / `alac` / `fLaC` / `drms`. There is no `ec-3` arm.
The `_` fall-through logs a warn, `skip_atom`s, and `continue`s the
loop. The zeros are never replaced. `Mp4Properties` carries them to
`From`, which wraps them in `Some(_)`, and `FileProperties` reports
`Some(0)` to the user.

### The shape of the comment

Three paragraphs.

First paragraph: where the zero comes from. Cite `:533`/`:542` for
the placeholder reads, `:567` for the codec dispatch with the exact
list of arms, and the `continue` that leaves the zeros in place.

Second paragraph: why the leak survives conversion. Cite `:190`/`:192`
for the plain internal types, `:203`/`:205` for the unconditional
`Some(_)` wrap, and contrast with the public contract at
`file_properties.rs:11`/`:13`.

Third paragraph: two fix shapes and a PR offer.

Minimal fix: at `:203` and `:205`, guard the wrap on positive values.
`if input.sample_rate > 0 { Some(input.sample_rate) } else { None }`,
same for channels. Trivial change, fixes the reported case, and fixes
any other codec the `:567` match doesn't dispatch — today: `opus`,
`wave`, `dts`, and any future codec added to the placeholder reads but
not yet to the dispatch match.
